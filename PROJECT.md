## 1. Project Overview

### 1.1 What Is RMW LLC Consulting?

RMW LLC Consulting is the professional consulting website for Ryan M. Waite — a Systems Architect and Software Engineer with 10+ years of experience. The site functions as a high-quality digital presence that attracts enterprise and startup clients seeking expertise in AI-assisted engineering, AWS cloud architecture, full-stack development, and DevOps. It is a single-page application built with Next.js 14 (App Router), Tailwind CSS, and a contact form backed by a server-side API route that sends email via SMTP.

### 1.2 How It Works

```
VISITOR lands on rmwllc-consulting.com
  → Cloudflare Tunnel receives request
  → Routes to nginx-external Ingress (NodePort 32080)
  → nginx forwards to rmw-llc-consulting Service (ClusterIP :3000)
  → Next.js standalone server renders the page (SSR)
  → Visitor browses sections: Hero → Services → About → Experience → Certifications → Contact

VISITOR submits the contact form
  → POST /api/contact (Next.js API Route, server-side)
  → Input validated (name, email, message required)
  → nodemailer sends HTML email via Mailpit SMTP (cluster-internal)
      ├─ Success → { success: true } → form shows confirmation
      └─ Failure → { error: ... } → form shows error with fallback email link
```

### 1.3 Key Entities

| Entity | Description |
|--------|-------------|
| Page | The single-page Next.js app rendered on every request |
| Section | Logical UI regions: Hero, Services, About, Experience, Certifications, Contact |
| ContactSubmission | Form payload (name, email, company, service, message) sent to the API route |
| EmailMessage | HTML email generated by `buildContactEmailHtml` and sent via nodemailer |
| KubernetesDeployment | The container running the Next.js standalone server in the cluster |

### 1.4 Domain-Specific Logic

- **Contact form validation**: `name`, `email`, and `message` are required. `company` and `service` are optional. Empty optional fields render as `—` in the email body.
- **HTML escaping**: All user-submitted fields are escaped via `escapeHtml()` before being embedded in the email body to prevent XSS in email clients.
- **SMTP auth is optional**: When `SMTP_USER` is not set (local dev with Mailpit), nodemailer omits the `auth` config entirely. When set (in-cluster), it uses `SMTP_USER` / `SMTP_PASSWORD` from the Kubernetes secret.
- **Reply-To header**: All contact emails set `replyTo: email` so Ryan can reply directly to the sender without copying the email address manually.

## 3. Non-Functional Requirements

- **NFR-01**: **SSR / Hydration** — The Next.js app uses Server Components by default. Only Nav and Contact are Client Components (`'use client'`). All other components are pure server-rendered.
- **NFR-02**: **No unnecessary state** — Client components manage only UI state (form values, menu open/close, submission status). No global state library.
- **NFR-03**: **Cost efficiency** — The cluster deployment uses `replicas: 1` per the single-worker-node constraint. No database, no cache — the pod is stateless. Cost at rest is near-zero beyond the existing cluster overhead.
- **NFR-04**: **Testability** — `src/lib/mailer.ts` is a pure function with no side effects. It is independently testable without mocking HTTP or SMTP.
- **NFR-05**: **Local dev parity** — docker-compose includes Mailpit as the local SMTP server, matching the cluster's Mailpit deployment. The same code paths run locally and in production.
- **NFR-06**: **Environment isolation** — All secrets (SMTP credentials) are injected via environment variables. No secret is hardcoded in any file committed to the repo.
- **NFR-07**: **Observability** — SMTP errors are logged to `console.error` with a `[contact]` prefix. Next.js structured logging is enabled in production via `NODE_ENV=production`.
- **NFR-08**: **Security** — All user input is HTML-escaped before embedding in email output. Input validation is server-side (API route). No SQL injection risk (no database). CSP headers are managed by Next.js defaults.
- **NFR-09**: **Component Layer Supremacy** — Email rendering logic lives exclusively in `src/lib/mailer.ts`. The API route (`src/app/api/contact/route.ts`) does three things only: parse input, call the mailer, return the response. No HTML string construction in the route handler.

## 4. System Architecture

### 4.1 Architecture Philosophy

This is a stateless Next.js web application deployed as a single container on the homelab k3s cluster. There is no database, no message queue, and no background workers. The architecture is intentionally minimal.

> **⚠ Component Layer Supremacy — Core Architectural Rule**
> All business logic (email template construction, input validation helpers, escape utilities) lives in `src/lib/`. The API route handler at `src/app/api/contact/route.ts` is a thin adapter: parse the request → call lib functions → return a response. Never put HTML generation, escaping logic, or string formatting inside the route handler itself.

### 4.2 Production Architecture (Conceptual)

```
Internet
  └─ Cloudflare DNS (rmwllc-consulting.com)
       └─ Cloudflare Tunnel ──────────────────────────────────┐
                                                               │
k3s Cluster (rmwhs.space)                                      │
  ├─ nginx-external Ingress (NodePort 32080) ←────────────────┘
  │    └─ Routes: rmwllc-consulting.com → rmw-llc-consulting:3000
  │
  ├─ cert-manager (letsencrypt-prod / DNS01)
  │    └─ Issues TLS cert for rmwllc-consulting.com
  │
  └─ Namespace: rmw-llc-consulting
       ├─ Deployment: rmw-llc-consulting (1 replica, rmw-home-server)
       │    └─ Container: Next.js standalone server (:3000)
       ├─ Service: ClusterIP :3000
       ├─ ConfigMap: SMTP_HOST, SMTP_PORT, SMTP_FROM, CONTACT_EMAIL
       └─ Secret: SMTP_USER, SMTP_PASSWORD (from Vault via pipeline)

Contact form submission path:
  Browser POST /api/contact
    → Next.js API Route (server-side)
    → nodemailer → Mailpit SMTP (email-mailpit.email-mailpit.svc.cluster.local:1025)
    → Email captured in Mailpit web UI (https://email-mailpit.rmwhs.space)
```

### 4.3 Local Development Architecture

```
Developer machine
  ├─ docker-compose up
  │    ├─ app (Next.js, port 3000) ──────→ SMTP → mailpit:1025
  │    └─ mailpit (port 8025 web UI)
  │
  └─ npm run dev (hot reload alternative, no Docker)
       └─ SMTP_HOST=localhost → needs local Mailpit or skip SMTP
```

### 4.4 Contact Form Async Flow

```
BROWSER
  POST /api/contact { name, email, company, service, message }
    → [route.ts] Validate required fields
        ├─ Missing fields → 400 { error: 'Missing required fields' }
        └─ Valid → [mailer.ts] buildContactEmailHtml(params)
              → HTML email string (all fields escaped)
              → nodemailer.createTransport(SMTP config)
              → transporter.sendMail({ from, to, replyTo, subject, html })
                  ├─ Success → 200 { success: true }
                  └─ Error   → console.error + 500 { error: 'Internal server error' }
```

## 7. Data Model

There is no database in this application. The only structured data is the in-memory form state managed by React's `useState` in the Contact component, and the `ContactEmailParams` type used by the mailer function.

### 7.1 ContactEmailParams (TypeScript type, not a DB table)

```typescript
type ContactEmailParams = {
  name: string      // required, trimmed before use
  email: string     // required, used as replyTo
  company: string   // optional — renders as '—' if empty
  service: string   // optional — renders as '—' if empty
  message: string   // required
}
```

### 7.2 API Request Payload

```typescript
// POST /api/contact body
{
  name: string      // required
  email: string     // required, valid email format
  company?: string  // optional
  service?: string  // optional, one of the dropdown values
  message: string   // required
}
```

### 7.3 API Response Shapes

```typescript
// Success
{ success: true }

// Validation failure (400)
{ error: 'Missing required fields' }

// Server error (500)
{ error: 'Internal server error' }
```

### 9.2 Jenkins CI/CD Pipeline

The pipeline uses the standard `jenkins-agent-base` agent with a DinD sidecar. Stages in order:

1. **Checkout** — clone repo, print last 5 commits
2. **Pre-flight Checks** — verify kubectl, docker, trivy, sonar-scanner are available
3. **Wait for Docker Daemon** — poll `docker ps` until DinD is ready (--mtu=1400)
4. **Prepare K8s Namespace & Registry Secret** — create namespace and harbor-credentials imagePullSecret from Vault
5. **Apply App Secret** — pull SMTP + OpenSearch creds from `kv/common-app-deploy-secrets`, create Kubernetes secrets
6. **SonarQube Scan** — `sonar-scanner` analysis (skippable via `SKIP_SONAR`)
7. **Quality Gate** — wait for SonarQube gate (skippable via `SKIP_QUALITY_GATE`)
8. **Build & Login** — docker login + `docker build` with `SKIP_UNIT_TESTS` arg forwarded
9. **Trivy Image Scan** — scan built image via Trivy server (skippable via `SKIP_TRIVY`)
10. **Push to Harbor** — push both `:<BUILD_NUMBER>` and `:latest` tags
11. **Deploy to Kubernetes** — apply all k8s manifests, wait for rollout

**Critical stages (never skippable):** Build & Login, Deploy to Kubernetes.

### 9.3 New App Bootstrap Checklist

| # | Step | Failure if skipped |
|---|------|--------------------|

## 12. Project Rules & AI-IDE Guidelines

1. **Component Layer Supremacy**: All HTML generation and escaping logic lives in `src/lib/`. The API route handler is a thin adapter only. Never add HTML string construction to `route.ts`.

2. **No direct DOM manipulation**: This is a React/Next.js app. No `document.querySelector`, no `getElementById`. All interactivity is through React state and event handlers.

3. **No secrets in code**: Use environment variables. The contact email, SMTP credentials, and any other sensitive values must come from env vars or Kubernetes secrets. Never hardcode them.

4. **TypeScript strict mode**: No `any` type. All function signatures must have explicit parameter and return types. The `tsconfig.json` has `"strict": true`.

5. **Client components are the exception**: Default to Server Components. Only add `'use client'` when the component needs `useState`, `useEffect`, browser APIs, or event handlers. Current client components: `Nav`, `Contact`.

6. **No new routing**: This is a single-page application. Do not add new Next.js pages or routes beyond the existing `app/page.tsx` and `app/api/contact/route.ts`.

7. **Tailwind only**: All styling uses Tailwind utility classes. Do not add CSS-in-JS, styled-components, Emotion, or custom CSS modules. `globals.css` contains only Tailwind directives and a scroll-behavior reset.

8. **Do not add a database**: This site has no database and should not have one. Contact form submissions go to email only.

9. **Do not change the content without instruction**: The content in components (company names, dates, certifications, descriptions) is sourced from `RESUME.md` and represents real facts. Do not modify it speculatively.

10. **AI guardrails**:
    - Do not create new architectural patterns not defined in this document.
    - Do not add new npm dependencies without explicit instruction.
    - Do not modify `k8s/` manifests in ways that conflict with `KUBERNETES_CONTEXT.md`.
    - Do not add a Fluent Bit sidecar unless explicitly asked — the `opensearch-credentials` secret is created by the pipeline as a forward-compatible preparation only.
    - Do not change `replicas` from 1 — the cluster has a single worker node.

## 14. Testing Plan

### 14.1 Unit Tests

**Tool:** Vitest 1.x  
**Location:** `tests/unit/`  
**Run command:** `npm run test:unit`

Covered in `mailer.test.ts`:
- All contact fields appear in the generated HTML
- HTML special characters (`<`, `>`, `&`, `"`, `'`) are escaped in all fields
- Empty optional fields render as `—`
- Output is a non-empty string with valid HTML document structure
- Ampersands in company/service values are escaped to `&amp;`

### 14.2 Integration Tests

No integration tests are defined. The contact API route is a thin adapter with no complex logic beyond what the unit-tested `buildContactEmailHtml` covers. SMTP behavior is validated via the local Mailpit docker-compose stack.

### 14.3 E2E / Manual Tests

| Test | Steps | Expected |
|------|-------|---------|
| Homepage loads | `curl https://rmwllc-consulting.com` | HTTP 200, HTML containing "AI-Augmented Engineering" |
| Contact form submission | Fill all fields, submit | Success panel appears; email visible in Mailpit |
| Contact form validation | Submit with empty message | Form stays open (browser HTML5 validation) |
| API validation | `curl POST /api/contact` with missing `message` | `400 { error: "Missing required fields" }` |
| HTTPS redirect | `curl -I http://rmwllc-consulting.com` | `301` redirect to `https://` |
| Mobile nav | Open site on 375px viewport | Hamburger visible; desktop links hidden |

### 14.4 Test Data Strategy

Unit tests use a fixed `base` object:
```typescript
const base = {
  name: 'Jane Smith',
  email: 'jane@example.com',
  company: 'Acme Corp',
  service: 'AI-Assisted Engineering',
  message: 'I need help with my project.',
}
```

Each test case spreads `base` and overrides only the fields under test. This keeps tests concise and the intent obvious.

### 14.5 CI Test Execution

Tests run inside the Docker build as a `RUN` step in the builder stage. A failed test fails `docker build`, which fails the pipeline before scan, push, or deploy. The `SKIP_UNIT_TESTS` build arg gates this — defaults to `false` (tests always run in CI).
